# The T113 platform layer

Workstream D. Status: 2026-09-18. **Nothing here has run.** There is no T113
in this session and there never will be; compiling is the only verification
available, and §9 says exactly what that proves and what it does not.

This is the third of the three implementations of `port/include` that
[docs/PLAN.md § 0.5](../docs/PLAN.md) calls for. The first two exist and pass
the same conformance tests — `port/host` on a laptop, `emu/` on a bare-metal
Cortex-A7 under QEMU. This one is the one that needs silicon.

## 2. Build

```sh
cd port/t113
make                 # build/mt32-t113.elf, .bin, and libmtp_t113.a
make lib             # the driver object set alone
make size            # sections and the ten largest symbols
make uimage          # wrap for U-Boot `bootm` (boot/BRINGUP.md 4.1)
make T113_MMU=0      # build the exact bootm handover state and never change it
```

There is no `make run`. `boot/BRINGUP.md` § 6.4: QEMU has no T113, R528 or D1
machine model and is not going to acquire one.

Flags, from `emu/`'s set plus `-Werror`:

```
-mcpu=cortex-a7 -mfpu=neon-vfpv4 -mfloat-abi=hard -marm
-O2 -ffreestanding -std=gnu99 -fno-builtin -fno-common
-Wall -Wextra -Werror -Wshadow -Wundef -Wpointer-arith -Wcast-align
-Wstrict-prototypes -Wmissing-prototypes -Wredundant-decls
-nostdlib -nostartfiles -Wl,--no-undefined
```

`-Wl,--no-undefined` is the part that matters. The link pulls in
`port/src/mtp_render.c`, `port/src/mtp_midi_parser.c` and
`port/host/engine_fake.c` — the same objects the host harness and the QEMU
image build — against these drivers. If it links, every function
`port/include` declares has an implementation here.

## 4. The peripherals, and the clock tree

### 4.1 Addresses used

| Block | Base | Interrupt | Source |
|---|---|---|---|
| PIO (pinmux) | `0x02000000`, bank stride `0x30` | — | [L][U][F] |
| CCU | `0x02001000` | — | [L][U][F] |
| I²S1 | `0x02033000` | SPI 27 → INTID 59 (unused) | [L][F] |
| UART0 (console) | `0x02500000` | SPI 2 → INTID 34 (unused, polled) | [L][U][F] |
| UART2 (MIDI in) | `0x02500800` | SPI 4 → **INTID 36** | [L][U][F] |
| DMAC | `0x03002000`, channels at `+0x100 + ch*0x40` | SPI 50/51 → **INTID 82 and 83** | [L][F] |
| GIC-400 distributor | `0x03021000` | — | [L][F] |
| GIC-400 CPU interface | `0x03022000` | — | [L][F] |
| SMHC0 (SD) | `0x04020000` | SPI 40 → INTID 72 (unused, polled) | [L][U][F] |
| DRAM | `0x40000000`; image at `0x40200000` | — | `boot/BRINGUP.md` 4.2 |

Three interrupts are enabled in total: 36, 82, 83. Everything else is polled,
which is `port/DESIGN.md` § 6.1's argument made concrete — there is one hard
deadline in this system and it is the audio ring.

### 4.2 The clock tree we rely on

```
DCXO 24 MHz  (CNTFRQ, and the CCU's "hosc")
 ├─ PLL_CPUX, PLL_DDR0, PSI/AHB, APB0, APB1   left exactly as U-Boot set them
 │    └─ APB1 ──> UART0 (115200) and UART2 (31250)   divisor computed at
 │                                                    runtime from the APB1
 │                                                    register, not assumed
 ├─ PLL_AUDIO0, N = 40 + 0.96, M = 10                  ← the one inference
 │    = 98.304 MHz (4x)
 │    └─ pll-audio0 = 4x / 4 = 24.576 MHz
 │         └─ i2s1 module clock, M = 1, P = 0 = 24.576 MHz
 │              └─ BCLK = mod / 8 = 3.072 MHz
 │                   └─ LRCK = BCLK / 64 = 48.000 kHz      ← the design's rate
 └─ hosc ──> mmc0 module clock, divided down to ≤ 16 MHz
```

Two deliberate decisions in that picture:

**We do not touch PLL_CPUX, PLL_DDR0 or the bus clocks.** `boot/BRINGUP.md`
§ 4.1 has us entered by U-Boot `bootm`, which has already run `clock_init()`
and the DRAM training that depends on it. Re-programming the bus clocks under
our own feet on a live DRAM controller has no upside. We read them and log
them.

**The UART divisor is computed, not assumed.** `port/DESIGN.md` § 3.3 says
"31250 is exact from a 24 MHz reference (divisor 48 at 16× oversampling)",
which is true *and is true only if APB1 is running at 24 MHz*. U-Boot decides
that. `src/ccu.c` reads the APB1 register, walks the mux to its parent, and
`src/uart.c` divides from the answer and logs the resulting baud error in
parts per thousand. A UART tolerates roughly ±2%; the failure mode of getting
this wrong is "MIDI works for short messages and corrupts sysex", which is a
miserable thing to debug.

### 4.3 Pinmux

Every function number is [V-D1] from `pinctrl-sun20i-d1.c`, which describes
the **die**. Whether the ball exists on the T113-i's LFBGA is §7.

| Signal | Pin | Function | Citation |
|---|---|---|---|
| Console TX / RX | PB8 / PB9 | 6 | `pinctrl-sun20i-d1.c:113, :123` |
| MIDI in (UART2 RX) | PB1 | 7 | `:37` |
| I²S1 LRCK | PG12 | 2 | `:742` |
| I²S1 BCLK | PG13 | 2 | `:752` |
| I²S1 DOUT0 | PG15 | 2 | `:772` |
| (I²S1 MCLK, unused) | PG11 | 2 | `:733` |
| SD D1 D0 CLK CMD D3 D2 | PF0..PF5 | 2 | `:580-…`, grouped as `mmc0_pins` in `sunxi-d1s-t113.dtsi:121-124` |

Notes for workstream B, which owns the board:

- **MIDI has no TX.** `port/DESIGN.md` § 5 lists "no MIDI output" among the
  things deliberately absent, so PB0 (UART2 TX) is free.
- **No MCLK to the DAC.** The PCM5102A runs from its internal PLL on BCLK
  alone, which `port/DESIGN.md` § 2.1 gives as the reason for choosing it. PG11
  is available if a later DAC needs one, and asking for it without naming a
  rate is a deliberate link error (§7).
- **We chose I²S1, not I²S0.** I²S0 at `0x02032000` appears only in
  Allwinner's own HAL, a file with no licence grant (`boot/BRINGUP.md` § 5.1).
  I²S1 has a mainline DT node, a driver binding, a DMA port number and a pin
  table, and the FreeRTOS T113 header confirms its base. This answers
  `port/DESIGN.md` § 8's question to workstream B about the I²S pin group.
- **U-Boot's MangoPi MQ-R defconfig sets `CONFIG_CONS_INDEX=4`**, i.e. UART3.
  Our console is UART0 on PB8/PB9. Two UARTs can be up at once; if you want
  one cable, change four lines in `include/t113_board.h`.

## 5. Verified, inferred, unknown

### 5.1 Verified by source

Every base address, every interrupt number, every register offset and bit
field in `include/t113_soc.h` carries a file-and-line citation, and §3's table
shows the ones that are double-sourced. That covers: the PIO layout and
function numbers; the CCU's gate, reset and module-clock register offsets and
field positions; the DMAC's register map, descriptor layout, configuration-word
encoding and per-channel stride; the I²S register map including the three
places where the D1 variant differs from the sun4i defaults; the SMHC register
map and reset sequence; the DesignWare UART register model; the GIC frame
addresses; and the SD command sequence.

### 5.2 Inferred, with the reasoning

**(a) The audio PLL for the 48 kHz family.** This is the one that matters, and
it is written out at length in `src/ccu.c`'s header. In short:

`port/DESIGN.md` § 2.1 requires exactly 48000 Hz out of the DAC. That needs an
audio clock in the 24.576 MHz family. Mainline cannot produce one on this SoC:

1. The I²S module clock's only parents are `pll-audio0`, `pll-audio0-4x`,
   `pll-audio1-div2` and `pll-audio1-div5` (`ccu-sun20i-d1.c:535-540`). There
   is no path from PLL_PERIPH0.
2. PLL_AUDIO1 is integer-N off the 24 MHz DCXO. 24.576/24 = 128/125, so an
   exact multiple of 24.576 MHz needs N a multiple of 125; the smallest is
   3072 MHz, above the driver's own `.max_rate` of 3000 MHz. (Its header
   comment says "usually 614.4 MHz", which the same arithmetic says is not
   reachable either — 614.4/24 = 25.6.)
3. PLL_AUDIO0 is fractional-N, but mainline drives its sigma-delta modulator
   from a lookup table, and the D1 table has exactly one entry:
   `{ .rate = 90316800, .pattern = 0xc001288d, .m = 6, .n = 22 }`. That is
   the 44.1 kHz family.

So the pattern for the 48 kHz family is in no T113 or D1 source. It was
derived by reading the table across every sunxi CCU that has one:

| SoC | rate | m | n | pattern | 24e6·(n+f)/m | ⇒ f |
|---|---|---|---|---|---|---|
| D1 | 90 316 800 | 6 | 22 | `0xc001288d` | 24·22.5792/6 | 0.5792 |
| A100 | 180 633 600 | 3 | 22 | `0xc001288d` | 24·22.5792/3 | 0.5792 |
| A100 | 45 158 400 | 18 | 33 | `0xc001bcd3` | 24·33.8688/18 | 0.8688 |
| A100 | 49 152 000 | 20 | 40 | `0xc001eb85` | 24·40.96/20 | 0.96 |
| A100 | 196 608 000 | 5 | 40 | `0xc001eb85` | 24·40.96/5 | 0.96 |
| H616 | 90 316 800 | 3 | 22 | `0xc001288d` | (with a fixed /2) | 0.5792 |
| H616 | 98 304 000 | 5 | 40 | `0xc001eb85` | (with a fixed /2) | 0.96 |

The pattern depends only on the fractional part of N and never on M: the same
`0xc001288d` appears with m=6, m=3 and m=3, and the same `0xc001eb85` appears
with m=20, m=5 and m=5. Four independent (SoC, m) pairs agree.

Therefore, on the D1/T113 layout: **N = 40, fraction 0.96 (pattern
`0xc001eb85`), M = 10** gives 24 MHz × 40.96 / 10 = **98.304 MHz**, and
`pll-audio0` = /4 = **24.576 MHz** = 512 × 48000. M = 10 is even, which
`ccu-sun20i-d1.c:168` says is required for a 50% duty cycle; N = 40 clears the
stated minimum of 12. Register fields are effective-minus-one (both
`_SUNXI_CCU_MULT_MIN` and `_SUNXI_CCU_DIV` default `.offset = 1`), so 39 and 9
are written.

**What would settle it:** the T113/D1 user manual's CCU chapter, the
PLL_AUDIO0 Pattern Register bit table. Failing that, a scope on BCLK: at 48
kHz with 32-bit slots it must read 3.0720 MHz.

**(b) The MMC module clock's hidden divider.** Linux models a fixed
post-divider of 2 on register 0x830 (`ccu-sun20i-d1.c:415-423`); U-Boot's
comment (`sunxi_mmc.c:96-100`) applies it only on the PLL path and not on the
24 MHz oscillator path. The two therefore differ by a factor of two about what
comes out. `src/ccu.c` rounds the divider so the card clock is at most what was
asked for, which makes the disagreement cost boot time and never correctness.

**(c) The DMA completion interrupt granularity.** The per-channel enable has
HALF, PKG and QUEUE bits. Linux picks PKG for a cyclic transfer and QUEUE
otherwise (`sun6i-dma.c:461`), and its cyclic period callback depends on PKG
firing once per descriptor. We use PKG. If it fires at a different
granularity, `mtp_audio_queued()` walks the wrong way and the underrun counter
runs away — §6 step 6 checks it.

**(d) The Cortex-A7 D-cache line length** is taken as 32 bytes in
`t113_dcache_clean_range()`, which is a safe under-estimate of the TRM's 64
and costs one extra `MCR`. Nothing in the audio path uses it; the ring is
uncached.

**(e) The I²S CLK_DIV BCLK field width.** The sun4i map says 3 bits at [6:4],
but the sun8i divider table has values up to 15, which needs 4. Our value is 5,
which fits either reading, and `src/i2s.c` writes the whole register rather
than a masked field so the ambiguity cannot bite.

### 5.3 Where two sources disagree

**PLL_AUDIO0's enable bits.** Three sources, two answers, at the same register
offset:

- `ccu-sun20i-d1.c:174-175`: `.enable = BIT(27)`, `.lock = BIT(28)`
- `ccu-sun50i-h616.c:232-233`: `.enable = BIT(31)`, `.lock = BIT(28)` — for a
  PLL_AUDIO at the **same** offset 0x078, with the same N/M/SDM field layout
  and the same pattern register at 0x178
- **[F]** `common/aw/ccu.c:279-286`, running on real T113 silicon:
  `|= BV(31) | BV(30)` ("enable pll, ldo"), then `|= BV(29)` ("lock enable"),
  then `while (!(... & BV(28)))` ("wait for pll stable")

The reading that makes all three true is the usual newer-Allwinner PLL layout:
31 = PLL enable, 30 = LDO enable, 29 = lock-detect enable, 28 = lock status,
27 = PLL output gate. Linux's D1 driver models only the output gate as
"enable" because U-Boot has already turned the PLL on for it; a payload that
is the first thing to touch PLL_AUDIO0 cannot assume that. **We set all four
and wait on 28.** Setting a bit that is already set costs nothing; not setting
one that is needed is a PLL that never locks — which looks exactly like a
wrong SDM pattern, and confusing those two failure modes would waste a day.

**The DMAC's interrupt line.** Mainline's device tree declares one interrupt,
SPI 50 → INTID 82, because Linux runs non-secure. **[F]**'s interrupt table
has two: `DMAC_NS_IRQn = 82` and `DMAC_S_IRQn = 83`. Which line a channel
raises depends on the DMAC's channel-security register (`SUNXI_H3_SECURE_REG`
at offset 0x20, named but never written in `sun6i-dma.c:52`) and on which
world we are in — and `boot/BRINGUP.md` § 4.4 says our security state is the
open question. `src/dmac.c` enables both and points them at one handler, which
is idempotent because it clears the status word before dispatching. Two GIC
writes are cheaper than a silent no-interrupt failure. (Evidence that 82 alone
would probably do: **[F]** enables only `DMAC_NS_IRQn` and its DMA runs.)

### 5.4 Unknown — needs a datasheet or a board

These are listed again, with what each one costs, in §7.

## 6. Bring-up order

Nine steps. Each one has a thing to prove, a thing that proves it, and a
statement of what its failure means — because on a board that has never run,
"it doesn't work" is not a diagnosis.

**1. It boots and talks.** Wrap with `make uimage`, load over `xfel` per
`boot/BRINGUP.md` § 6.3, and `bootm`. Expect the banner and the `entry:` block
on UART0 at 115200.
*No output at all*: wrong console UART for your board (change four lines in
`include/t113_board.h`), or the pins are not bonded out (§7), or U-Boot never
reached the payload. *Garbage output*: APB1 is not what `src/ccu.c` computed —
the `uart0: console ... error N/1000` line says by how much.

**2. Read the entry state.** This is the ten-line `mrs`/`mrc` dump
`boot/BRINGUP.md` § 4.4 asks for, and it closes the project's oldest open
question. Look at: `MIDR` (must say Cortex-A7), `SCTLR` (MMU and D-cache must
be **off** — if they are on you used `go` or `bootelf`, and the log says so in
those words), `ID_PFR1` security extensions, `CNTFRQ` (expect 24 000 000), and
`MPIDR` (must be core 0).
*This step costs nothing and removes three guesses.* Record the answer in
`boot/BRINGUP.md` § 4.4.

**3. Read the assumptions block.** The boot log prints every
`MTP_T113_UNVERIFIED` constant compiled into the image, with its value and why
it is unverified. Today that is three, all of them PLL_AUDIO0's. Everything
after this step is being run against those numbers.

**4. Clocks.** The `ccu:` lines report PLL_CPUX and PLL_PERIPH0 raw, the
decoded PLL_PERIPH0 and APB1 rates, and PSI/AHB. Sanity-check APB1 against
whatever U-Boot printed for itself.
*APB1 mux = 2*: `src/ccu.c` does not model `psi-ahb` and says so; the UART
divisor after that point is a guess and step 1 will already have looked wrong.

**5. The audio PLL — the step most likely to fail.** `ccu: PLL_AUDIO0 locked,
4x = 98304000 Hz (inferred)`.
*"PLL_AUDIO0 did not lock"*: either the enable bits (§5.3) or the SDM pattern
(§5.2a) is wrong, and the log prints both registers so you can tell them apart
— a control register that reads back your N and M with bit 31 set but bit 28
never rising points at the pattern; one that does not read back at all points
at the enable bits. Then scope BCLK on PG13: **3.0720 MHz** is right. The most
likely wrong answers are 5.0912 MHz (the fraction ignored, N=40 integer) or
nothing at all.
*If the pattern is wrong and cannot be fixed*, note that the fallback is not
what it looks like: 44.1 kHz is exactly reachable with the mainline pattern,
but `port/DESIGN.md` § 2.1 rules out the resampler that 44.1 kHz would need,
and the documented 32 kHz fallback (`AnalogOutputMode_COARSE`) is in the
*same* 24.576 MHz family. **Getting this family is not optional.** §8 says what
that means for `docs/PLAN.md`.

**6. I²S and DMA.** The `i2s:` dump prints CTRL, FMT0, FMT1, FIFO_CTRL,
CLK_DIV, CHAN_CFG, TX_CHAN_SEL, FIFO_STA, TXCNT. Then read the `[c]` counter
line: `dma-irq` must climb at the block rate (375/s at 128 frames and 48 kHz)
and `played` with it, `underruns` must stay at 0, and `minq` must stay at 1 or
above.
*`dma-irq 0`*: the engine never completed a descriptor. Check
`t113_dmac_cur_src()` — if it is not advancing, the DRQ never fired, which
means the I²S TX DRQ enable or the DRQ port number is wrong; if it is
advancing, the interrupt is not reaching us and the secure/non-secure line
question (§5.3) is the first suspect even though both are enabled.
*`dma-irq` climbing but `underruns` climbing too*: PKG is not firing once per
descriptor (§5.2c), or the renderer is genuinely late — `minq` tells you
which, because a late renderer shows `minq 0` before the underruns start.
*TXCNT not advancing*: BCLK is not running; go back to step 5.

**7. Audio out of the speaker.** This is the first step that needs ears.
`port/DESIGN.md` § 4.3's promise is that the module boots, accepts MIDI and
outputs silence with no ROMs; the fake engine in this build outputs a test
tone instead, so a DC level or a buzz means the I²S format is wrong — the
usual suspects are the LRCK polarity and the channel-select offset, which
`sun50i_h6_i2s_set_soc_fmt()`'s I²S branch fixes at START_LOW/mode LEFT/offset
1 and `src/i2s.c` reproduces.

**8. MIDI in.** Send a note on. `[c]` shows `midi` climbing as
bytes/short/sysex, `ovr 0`, `fe 0`.
*`fe` climbing*: framing errors. On an opto-isolated DIN input that usually
means the optocoupler, not the software — `mtp_midi.h` says so. But check the
`uart2: MIDI in ... error N/1000` line first: if the divisor error is over
about 20/1000 the baud rate is wrong and the optocoupler is innocent.
*`ovr` climbing*: the render loop is overrunning its block period, which
should already have shown as underruns in step 6.

**9. SD and ROMs.** `storage: mounted, N MiB card` and the `/mt32.cfg` and
`/roms/…` presence lines.
*"no usable card"*: the log names which of the three stages failed — the
controller reset, the card protocol, or the FAT parse. A card that answers
CMD8 but never leaves busy on ACMD41 is a voltage problem; one that never
answers CMD8 is wiring or clock; a FAT parse that fails on a card that mounts
on a laptop means the partition type byte is one this driver does not list.

Only after step 9 does workstream A's gate become answerable on this board,
and that needs ROMs, which are Roland's and are not here.

## 7. What still needs a datasheet or a board

| # | Fact | Why it is not here | What it blocks | Cost if wrong |
|---|---|---|---|---|
| 1 | **The T113-i LFBGA ballout** | No T113-i datasheet was reachable; `docs/HISTORY.md` § 8 and `boot/BRINGUP.md` list the vendor sites as blocked | Every pin in §4.3 | A board respin. This is workstream B's, and it is the single most expensive unknown in this document |
| 2 | **PLL_AUDIO0 Pattern Register encoding** | Not in any T113 or D1 source; derived in §5.2a from four other SoCs | 48 kHz audio, i.e. all of it | One `xfel write32` to try another pattern — cheap to test, and step 5 tests it |
| 3 | **PLL_AUDIO0 Control Register bit table** | Two mainline drivers disagree (§5.3) | The PLL locking at all | Mitigated: we set the union of both readings |
| 4 | **The DMAC channel-security register** at offset 0x20 | Named but never written in mainline; no bit table anywhere | Which of INTID 82/83 a channel raises | Mitigated: both are enabled |
| 5 | **"Package end" vs "queue end"** DMA interrupt semantics | Inferred from Linux's cyclic path (§5.2c) | Whether the play cursor advances once per block | Step 6 detects it in seconds |
| 6 | **SMHC delay-line calibration** above 25 MHz | The one part of a sunxi MMC driver that genuinely needs the manual | Faster SD | Avoided: we stay inside SD default speed and pay boot time |
| 7 | **Secure or non-secure at handover** | `boot/BRINGUP.md` § 4.4, unresolved | GIC group configuration; which timer PPI would fire if we used one | Mitigated: we write GICD_CTLR = 3, leave everything in group 0, and use no timer interrupt at all |
| 8 | **PCM5102A group delay** | `port/DESIGN.md` § 2.5 already flags it: "≈0.4 ms, *verify against the datasheet*" | The latency budget's fixed term | Nothing structural; it is a number in a table |
| 9 | **The power-up sequence** | `docs/PLAN.md`: "the vendor warns wrong timing destroys the part" | Copper | Not ours — workstream B's — but it gates ever running any of this |

Items 2, 3, 4 and 5 are all one board-session away. Item 1 is the one that
cannot be answered by any amount of further reading.

## 8. What this should change elsewhere

**For `docs/PLAN.md` § 0.5 and the risk list.** A new risk belongs there, and
it is genuinely new:

> **The T113's audio PLL has no documented 48 kHz recipe.** The 44.1 kHz
> family is one table entry in mainline Linux; the 48 kHz family — which
> `port/DESIGN.md` § 2.1 chose, correctly, because it is what
> `AnalogOutputMode_ACCURATE` produces with no resampler — is in no T113 or D1
> source. `port/t113/src/ccu.c` derives it from four other Allwinner SoCs that
> share the sigma-delta pattern encoding, and the firmware announces at boot
> that it is running on an inference. **The fallback everyone assumes exists
> does not**: 32 kHz (`AnalogOutputMode_COARSE`) is in the *same* 24.576 MHz
> family, and 44.1 kHz would need the `SampleRateConverter` that
> `port/DESIGN.md` § 2.1 rules out on RTTI, `<iostream>` and a 32 KB stack
> buffer. If the inference is wrong, the options are: find the manual, or take
> the resampler and its costs, or clock the DAC from a crystal instead of from
> the SoC. That last one is a hardware change and so it is a decision for
> workstream B *before* the board, not after.

**For `port/DESIGN.md` § 8's open questions.** Two of the three questions
addressed to workstreams B and C are now answered from this side:

- *"the I²S pin group and whether the PCM5102A gets an MCLK"* — I²S1 on
  PG12/PG13/PG15, no MCLK, with the reasoning in §4.3.
- *"whether the payload is entered with the MMU and caches on or off, and who
  sets up the audio PLL"* — `bootm` hands over with both off
  (`boot/BRINGUP.md` § 4.1), and **we** set up the audio PLL, not the
  bootloader. So `port/DESIGN.md` § 2.3's non-cacheable mapping is ours to
  configure, and `src/mmu.c` configures it.

**For `hw/HARDWARE.md`.** §4.3's pin table is a request, not a statement:
every function number is verified against the die and none against the
package. If the T113-i's LFBGA does not bring out PG12/PG13/PG15, the I²S
choice moves to I²S2 (`0x02034000`, DRQ 5, INTID 60) and this port changes by
four lines in `include/t113_board.h` — provided *those* pins exist. That is
worth checking before the schematic is frozen.

**For `boot/BRINGUP.md` § 5.2.** Its verdict on the FreeRTOS T113 port —
"an excellent reference for GIC, timer, MMU and SMHC on this exact SoC, under
a licence we can actually use. Not a BSP." — is confirmed and can be
strengthened: `lib/aw/aw_t113s2.h` is a complete T113 register map with an
interrupt table, and it is the only **[V-T113]** corroboration this project has
for most of its addresses. It was worth cloning for that file alone.

## 9. What compiling proves, and what it does not

**It proves:**

- the platform interface is implementable on this SoC: the link with
  `-Wl,--no-undefined` succeeds, and a symbol-by-symbol comparison of what
  `port/include` declares against what `libmtp_t113.a` defines leaves exactly
  six names outstanding — `mtp_midi_msg_len`, `mtp_midi_parser_init`,
  `mtp_midi_parser_feed`, `mtp_render_init`, `mtp_render_pump`,
  `mtp_render_run` — which are the portable ones from `port/src`, by design;
- the same render loop, MIDI parser and fake engine that the host harness and
  the QEMU image use compile clean for Cortex-A7 at `-Wall -Wextra -Werror`
  with `-Wshadow -Wundef -Wpointer-arith -Wcast-align -Wstrict-prototypes
  -Wmissing-prototypes -Wredundant-decls`, freestanding, against no libc but
  our own;
- `docs/PLAN.md` § 0.5 rule 1 holds: there is no `#ifdef T113` anywhere above
  the seam, and no file in `port/include`, `port/src` or `port/host` was
  modified to make this build;
- the image is 41 424 bytes and the drivers are 27 644 bytes of text, so the
  lower layer is small enough to be the "thin, expensive layer" rule 3 asks
  for;
- the `MTP_T113_UNKNOWN` mechanism works: building `src/i2s.c` with
  `-DT113_I2S_MCLK_OUT` and no MCLK rate produces
  `undefined reference to 'mtp_t113_unknown__i2s1_mclk_rate_hz'`, which is a
  build that fails loudly on an unknown rather than one that silently contains
  a made-up number;
- `port/host/test.sh` still passes, unchanged.

**It does not prove:**

- that any of these addresses is right. Not one register has been written on
  this silicon;
- anything about speed. That is workstream A's number, it needs ROMs and a
  board, and `docs/PLAN.md` § 0.5 is explicit that emulation produces no
  timing evidence at all;
- that the audio PLL inference is correct. §6 step 5 is the test;
- that the SD or FAT code reads a real card. Neither has seen a block device;
- that the I²S format matches what a PCM5102A wants. Nothing has been through
  a speaker, which is `docs/HISTORY.md` § 7's fourth unknown and is still
  open.

## 10. Licences

Everything in `port/t113/` is 0BSD. `src/printf.c` and `src/retarget.c` are
adapted from `emu/src/`, which is also 0BSD and also this repository.

Nothing was copied from a GPL source. U-Boot and Linux were **read** for
register addresses, bit positions and reset values — facts about silicon, not
expression — which is the rule `boot/BRINGUP.md` § 5.4 already set for the I²S
driver: read it "for understanding rather than copying it, which sidesteps the
licence question". Every such fact carries a citation so that the reading is
reproducible and so that a reviewer can check the claim. The FreeRTOS T113
port's own files are public domain per its README, and were likewise read
rather than copied.

`port/vendor/` holds the three clones and is gitignored. No vendor source is
committed and none was modified.
